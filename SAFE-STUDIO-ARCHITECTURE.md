# Safe Studio — Architecture & Feature Reference

A standalone visual page builder in a single HTML file (~1.2MB, ~22,900 lines). Opens in any browser, no server required. Everything — CodeMirror editor, SafeScript 2.0 compiler + debugger, all CSS, all JS — is inlined.

## What It Is

A VB/HyperCard-style tool for building interactive web pages visually. Pages are made of sections (layout containers) and blocks (content units). Blocks have roles (heading, text, action, media, card, feature, etc.) and are powered by tools from the Qbix Platform ecosystem. SafeScript handlers attached to blocks and sections give them behavior. The debugger lets you step through that behavior, rewind it, fork timelines, and see DOM changes live.

## Canvas & Rendering

### Sections

A section is a layout container. Each has a `layoutKey` that maps to a LAYOUTS entry defining grid columns, padding, gap, min-height, alignment, and background. Sections render as `<div class="ss-section">` with a header bar (drag handle, move up/down, label, duplicate, delete) and a body `<div class="ss-sec-body">` whose CSS grid is set by the layout.

Section properties: `layoutKey`, `bg` (default/tint/gradient), `padding`, `gap`, `customCSS`, `customId` (PascalCase, used in SafeScript references), `classes` (CSS class list), `blocks[]`, `mobileLayout` (stack/accordion/tabs/carousel), `mobileBreakpoint`.

### Blocks

A block is a content unit inside a section. Each has a `role` (heading, text, action, media, stat, card, feature, nav, etc.) and a `tool` (the Qbix tool ID that powers it). Blocks render as `<div class="ss-block">` with inline content generated by `blockHTML()` → `toolDefaultContent()`.

Block properties: `role`, `tool`, `content` (raw HTML), `customId`, `customCSS`, `cssClass`, `classes`, `fontFamily`, `ariaLabel`, `toolOptions` (typed options for the tool), `mobileDisplay` (inline/accordion/dropdown/drawer/hidden), `mobileTriggerLabel`. A custom tool ID in `tool` makes the block render that tool's structured section layout; its local `content` is `null` so the tool definition stays the source of truth.

### Rendering pipeline

`renderCanvas()` → iterates `state.page.sections` → `renderSection(sec, si)` → iterates `sec.blocks` → `renderBlock(block, bi, si)` → `blockInnerHTML(block, si, bi)`. Ordinary blocks use `blockHTML()` → `toolDefaultContent()`. Custom-tool blocks use `buildToolTemplate()` to render the tool's sections as nested CSS-grid layout containers.

The last function checks TOOL_MOCKUPS first (returns SVG if registered), then falls back to tool-specific HTML placeholders, then to the block's raw `content` field.

### SVG Mockup Renderers

18 tool-specific SVG generators in the `TOOL_MOCKUPS` object. Each is a function `(toolOptions, width, height) → SVG string`. They use CSS variables (`var(--theme-brand)`, `var(--theme-bg-2)`) so they re-theme when you switch palettes. They respond to `block.toolOptions` — change the rating value in properties and the stars update live.

Registered mockups: Q/rating (stars), Q/progress (bar), Q/countdown (clock), Streams/chat (bubbles), Streams/participants (avatars), Streams/comments (threads), Streams/related (card grid), Q/tabs (tab bar), Q/expandable (collapsible), Q/carousel (perspective cards), Q/coverflow (receding covers), Q/video (play button), Q/ticker (marquee), Q/chart/bar, Q/chart/line, Q/pie (arc paths), Q/parallax (gradient), Q/badge (corner dot).

This mirrors the `Q.Tool.mockup` registry from the Qbix Platform, which uses `Q.Tool.DOMtoSVG` to convert rendered DOM into themed SVG. When Safe Studio runs as a Qbix plugin, it can load the real registry for mechanical mockups of any tool with a `Q.Template`.

### TOOL_PROPERTIES & Smart Defaults

Each tool can register typed property definitions in `TOOL_PROPERTIES`. Property types: `string`, `number`, `boolean`, `color`, `url`, `select`, `json`, `datetime`, and metatypes (`publisherId`, `streamName`, `userId`, `web3Address`, `relationType`, `streamType`).

Metatypes are defined in `FIELD_METATYPES`. Each provides a label, default value, and preset dropdown. For example, `publisherId` defaults to `$community` (Current Community) with presets for Main Community, Logged-in User, From URL, and From route. The properties wizard renders a preset dropdown + freeform text input for each metatype field.

Runtime expressions (`$community`, `$loggedInUser`, `$query.xxx`, `$route.N`, `$wallet`) are resolved at page load in exported HTML via `ssResolve()`. This bridges static Safe Studio pages to dynamic Streams content.

### Custom Tools

Users create custom tools from existing tools and elements. `createAndEditTool()` creates a new tool with a unique ID, `enterToolEditor(toolId)` swaps `state.page.sections` and `state.handlers` to point at the tool's internal structure, so all rendering functions operate on the tool. `exitToolEditor()` calls `buildToolTemplate()` to generate HTML from the tool's structured sections/blocks, wraps it in `<div data-tool-instance>`, and restores page state.

Custom tools appear in the "My Tools" category and can be dragged onto any page. Each instance gets its own scope via `data-tool-instance` — `context.tool` refers to the instance root, `context.children` refers to child elements by `data-child-id`.

### Nested section layouts

Select a page block and use **Create nested layout** to turn it into a custom tool instance, choose a starting section layout, then edit the tool to add, remove, or rearrange child sections. From section properties, **Add nested layout block** appends a new custom-tool block inside that section. Nested tools can contain further nested tools; the editor keeps a parent stack so each Back action returns one level. Page navigation unwinds the stack and saves the root page first.

Every child section retains its `layoutKey`, padding, gap, background, classes, custom CSS, and block IDs in the custom tool's `structure.sections[]`. Tool `classStyles` are embedded with selectors scoped to that tool instance, and SafeScript child lookup excludes descendants owned by nested instances. Recursive rendering is capped at 16 levels and stops circular tool references with a placeholder. Nested grids keep their desktop column definitions in the editor and exported HTML, then collapse to one column below 768px. The same custom tool can be reused elsewhere; editing its nested layouts updates all its instances. Existing page and tool JSON shapes remain valid, with nested layouts represented by the existing `customTools[]` and block `tool` fields.


## Mobile-Smart Blocks

### Per-block display modes

Each block has a `mobileDisplay` property:
- **inline** (default) — renders normally, stacks vertically
- **accordion** — shows a clickable trigger bar; body hidden until expanded. Trigger shows `mobileTriggerLabel` or the block role, with a rotating chevron. Max-height CSS transition for smooth animation.
- **dropdown** — similar but styled as a brand-colored button
- **drawer** — trigger click opens a bottom-sheet overlay (`position:fixed`) with backdrop blur, drag-to-dismiss handle, body scroll lock
- **hidden** — `display:none` on mobile

### Per-section mobile layout

Each section has a `mobileLayout` property:
- **stack** (default) — blocks stack vertically
- **accordion** — all blocks become accordions, exclusive mode (opening one closes siblings)
- **tabs** — blocks become tab panels with a horizontal tab bar; block titles as tab labels
- **carousel** — blocks in a horizontal scroll-snap container with dot indicators

At phone widths, section grids and nested tool-layout grids collapse to one column by default. The editor's mobile device preview applies the same grid behavior even when the browser window itself is wide.

### Runtime

`toggleMobileBlock(si, bi)` handles expand/collapse for accordion/dropdown, creates/shows drawer overlay for drawer mode. `switchMobileTab(si, tabIdx)` toggles block visibility and active tab. `scrollCarousel(si, dotIdx)` scrolls to carousel items.

All mobile behaviors are included in exported HTML output with inline CSS and JS. Exported page sections and custom-tool layouts also include the one-column mobile grid rule.


## SafeScript Integration

### Scope Building

`buildElementScope(code, toolRootEl)` creates the execution scope for SafeScript handlers. The scope includes:
- **Element references** via hierarchical IDs: `Section1_$Moo$Foo_$Bar` → CSS selector `[data-ss-id="Section1"] .Moo.Foo .Bar`. IDs precede classes, `$` starts class segments, `_` separates path levels.
- **context.block**, **context.section**, **context.page** — DOM element references
- **context.tool**, **context.children** — per-instance tool scope (when inside a `data-tool-instance` wrapper)
- **Users**, **Streams** — host objects for Qbix API access (when connected to backend)

### Handler Execution

`_runHandler(code, eventObj, el)` detects `el.closest('[data-tool-instance]')` for per-instance scope, builds the scope, compiles and runs via SafeScript. Each handler key is `${si}:${bi}:${event}` (e.g., `0:1:onClick`).

### Autocomplete

`getCompletions()` provides completions for: element references (from section/block IDs and classes), `Users.*`, `Streams.*`, stream instance methods, `context.tool`, `context.children.*`, and hierarchical refs.


## Time-Traveling Debugger

This is the core innovation. It combines four systems: SafeScript's debug engine (stepping), the Journal (DOM change tracking), the Timeline Tree (undo/redo with branching), and the Debug UI (locals panel, variable tooltips, step history).

### SafeScript Debug Engine

`SafeScript.debug(code, scope, options)` returns a `DebugSession`. The compiler instruments the code with checkpoints at every statement. The session provides:

- **step()** — execute the next statement and pause
- **stepOver()** — execute the next statement, skipping into function calls
- **stepOut()** — run until the current function returns
- **continue()** — run until the next breakpoint or end
- **stop()** — terminate the session
- **fork()** — clone the session at the current point (creates a child session with independent state but shared history up to the fork point)
- **rewindTo(stepIndex)** — rewind execution to a specific step, undoing all DOM changes after that point via the journal
- **editAndContinue(newSource)** — hot-swap the source code mid-debug and continue from the current point
- **evaluate(expr)** — evaluate an expression in the current scope (for watch expressions and the console)
- **createCheckpoint()** — snapshot the current state for later restoration
- **getNodeTimeline(node)** — get the history of changes to a specific DOM node

### The Journal

`Journal` (in `src/journal.js`) is a write-ahead log for all side effects. Every DOM mutation during SafeScript execution goes through the journal instead of modifying the DOM directly:

```
Journal.write(target, key, oldValue, newValue)
Journal.read(target, key)  → returns overlay value or falls through to real DOM
Journal.rewindTo(stepIndex) → rebuilds overlay from log[0..stepIndex], truncates
Journal.commit()  → applies all logged changes to the real DOM
Journal.discard() → drops all changes, restoring the DOM to pre-execution state
```

The journal stores entries as `{ target, key, was, to, step }` where `step` is the debug step index that caused the write. This means you can rewind to any step and the journal rebuilds the overlay to show the DOM state at that exact point.

### DOM Journal Adapter

`attachDOMJournal(context, journal, effectLog)` intercepts all DOM access in SafeScript's sandboxed context:

- **Property sets** (`element.textContent = 'x'`) → `journal.write(element, 'textContent', old, new)`
- **Style sets** (`element.style.color = 'red'`) → `journal.write(element, 'style:color', old, new)`
- **Attribute sets** (`element.setAttribute('class', 'x')`) → `journal.write(element, 'attr:class', old, new)`
- **innerHTML** → `journal.write(element, 'innerHTML', old, new)`

Property reads go through `journal.read()`, which returns the overlay value if one exists, or the real DOM value if not. This means the executing code sees its own writes reflected immediately, while the real DOM remains untouched until commit.

### How It Feels: Bret Victor Style

1. **Write a handler** — e.g., `onClick` on a button: `Section1_$Title.style.color = 'red'; Section1_$Counter.textContent = parseInt(Section1_$Counter.textContent) + 1;`

2. **Click Debug (F5)** — `dbgStartSession()` creates a debug session with a simulated event, instruments the code, pauses at the first statement.

3. **Step (F10)** — Each step executes one statement. The locals panel shows all variables and their current values. The code editor highlights the current line. If the statement mutated the DOM (changed a style, set text), the change shows on screen via the journal overlay, and the effect appears in the step history.

4. **Scrub the timeline** — Click any step in the step history panel. `dbgRewind(stepIndex)` calls `session.rewindTo(stepIndex)`, which rebuilds the journal overlay to that point. The DOM visually reverts to the state at that step. Click a later step and it replays forward. This is the scrubbing.

5. **Fork** — At any paused step, `dbgFork()` calls `session.fork()`, which clones the session. You now have two independent execution paths from the same point. The timeline tree shows the fork as a branch. You can switch between branches by clicking in the fork menu.

6. **Edit and Continue** — While paused, edit the code in the editor. `dbgEditAndContinue(newSource)` hot-swaps the compiled code and continues from the current point with the new logic. The old steps stay in history; new steps follow the new code.

7. **Commit or Discard** — When done exploring, `dbgCommit()` applies all journal entries to the real DOM. `dbgDiscard()` throws them away, restoring the DOM to its pre-debug state. Non-permanent changes until you decide.

### The Timeline Tree

The timeline tree (`_tlTree`) is a separate system from the debug step history. It tracks all user actions in the editor — not just debug steps, but any edit, layout change, tool swap, or event handler execution.

```javascript
_tlTree = {
  nodes: {},        // id → { id, parentId, children[], snapshot, label, type, timestamp }
  rootId: null,
  currentId: null,  // pointer to "now"
  redoChildId: null // for redo: which child we came from
}
```

Each node stores a full snapshot of `state.page` and `state.handlers`. Actions:

- **pushUndo(label, type)** — creates a new node as a child of the current node. Called by any state-changing operation (add section, move block, change property, run handler).
- **undo()** — moves to parent node, restores its snapshot. Remembers which child we came from for redo.
- **redo()** — moves to the remembered child, or the most recent child if none remembered.
- **tlJumpTo(nodeId)** — jumps to any node in the tree, restoring its snapshot. This is the scrubbing.
- **tlDeleteBranch(nodeId)** — deletes a node and all its descendants (unless the current node is in the subtree).
- **_tlSwitchBranch(parentId, childId)** — when a node has multiple children (a fork), switch to a different branch.

The tree renders as a vertical list showing the active path from root to current, with fork indicators (count badge + dropdown menu) where branches exist. Each node shows an icon by type (✏ edit, ⚡ event, ⟨/⟩ code, ○ init), a label, and a timestamp relative to session start.

### Auto-branching

This is where undo/redo becomes timeline forking. When you:

1. Make edits A → B → C (linear chain)
2. Undo to B
3. Make edit D

...the tree becomes:

```
A → B → C
      ↘ D    ← you are here
```

Node B now has two children: C (the old branch) and D (the new branch). The fork indicator on B shows "2▾" — click it to get a popup menu letting you switch between branches C and D. Each branch preserves its full state. You can jump to C, make more edits (branching C further), jump back to D, etc. The tree grows like a git commit graph.

### Breakpoint Types

Three types, stored in `state.breakpointMeta` as `Map<line, { type, expr }>`:

- **Regular (bp)** — pause when execution reaches this line
- **Conditional (cond)** — pause only when `expr` evaluates to truthy in the current locals scope
- **Logpoint (log)** — don't pause; log `expr` to console and show a toast, then continue

Breakpoints sync to the debug session via `syncBreakpointsToSession()`. The gutter in CodeMirror shows colored markers: red circle for regular, yellow diamond for conditional, blue triangle for logpoint.

### Variable Inspection

**Locals panel** — shows all variables in the current scope with their values, updated after each step. Values are formatted by `formatValue()` which handles primitives, arrays, objects, DOM elements, functions, and nested structures with expandable tree views.

**Watch expressions** — user-defined expressions evaluated after each pause via `session.evaluate(expr)`. Shown in a separate panel with live results.

**Variable tooltips** — hover over any variable name in the code editor while paused. `showVarTooltip()` evaluates the token under the cursor and shows a floating tooltip with the formatted value. For DOM elements, shows tag, classes, and key properties.


## Project System

### Multi-page projects

`state.project = { pages: [...], activePageIdx }`. Each page has its own sections, handlers, classStyles, customTools, and title. Pages appear as tabs in the header (dropdown on mobile).

`ensureProject()` creates the project structure on first use. `switchProjectTab(idx)` saves the current page into the project, loads the target page into state. `addProjectPage()` creates a new blank page. `removeProjectPage(idx)` removes with confirmation.

Tools are shared across all pages in a project.

### Import/Export

- **Export Page JSON** — serializes `state.page` + `state.handlers` as JSON
- **Export Tool JSON** — serializes a custom tool definition as JSON
- **Import JSON** — detects whether the JSON is a page or tool and loads it
- **Export HTML** — generates a standalone HTML page with all content, styles, theme, SEO meta tags, mobile behaviors, and SafeScript handler runtime
- **Clone Site** — paste any page's HTML source, get an editable Safe Studio page with sections, layout, content, theme, and SEO extracted mechanically (no LLM)

## Persistence

`save()` writes to `localStorage` (key: `ss-page`, `ss-handlers`, `ss-project`). Special handling when editing a tool: saves the stashed page state, not the swapped-in tool sections.

The editor exposes save status, manual recovery checkpoints, and restore. Shared previews are loaded as a separate page copy and are not written into the local project. Page assets are included in page/project JSON so an imported project retains its local image library.

When connected to a Qbix backend (future), `save()` posts diffs as `Websites/page/changed` messages to the page stream, enabling real-time collaboration, version history, and fork chains.

## Authoring assistance

- **Outline** walks sections and blocks in page order. Selecting an item focuses its properties; nested reusable layouts can be opened from the outline.
- **Add panel** groups page layouts, content blocks, and reusable nested layouts. The same nested layout can be inserted in multiple places, then edited as a shared custom tool.
- **Assets panel** stores local image data and alt text in the page model. Image blocks can refer to an asset by ID, so the same asset is reusable and included by JSON export.
- **Template gallery** groups templates by category, shows counts and small layout previews, and supports search.
- **Import review** validates page/project/tool data before it becomes active. Unknown layout references are migrated to a plain text layout, malformed structures are rejected, and warnings are shown for confirmation.
- **Walkthrough and sample page** explain the first steps and add a sample page alongside current work.
- **Share Preview** encodes a bounded page snapshot in a URL hash and opens it in Test mode as an isolated copy. This is intended for hosted editor links; `file:` links cannot be opened on another device as a shared app route.
- **Debugger error card** summarizes common runtime errors, identifies the current source line when the runtime exposes it, and provides line navigation and rerun actions.


## Standalone vs. Qbix-connected Test mode

**Standalone**: The HTML file opens in any browser. SafeScript interactions run locally, but tools that need a Qbix backend render as SVG mockups or HTML placeholders. Data persists in localStorage.

**Qbix-connected Test mode**: When the editor document is loaded after the Qbix app's normal client bootstrap, Test mode detects `Q.Tool.setUpElement`, `Q.activate`, and `Q.Tool.from`. It mounts each non-custom Qbix tool into its block using the saved `toolOptions`, including tools inside reusable nested layouts. It disposes those tool instances before returning to Design or rerendering the canvas, then restores the editor preview markup. SafeScript preview handlers continue to run on the surrounding Safe Studio blocks.

The connected adapter does not load `Q.js` or app credentials itself. The standalone file still has no Q global; it must run in a Qbix-controlled page/route where the app bootstrap and tool definitions are already available in the same document. Loading the framework script alone does not provide the app configuration or session. Connected tools use the current Qbix session and can perform the reads or writes their normal implementations allow, so test data is recommended.

The adapter is covered in Playwright with a Qbix API-shaped stub, including option forwarding, root and nested tool mounting, status UI, and cleanup. A live Qbix server was not available in this workspace, so actual authenticated tool behavior remains to be verified in the target app.

**Future full plugin integration**: Store pages as streams, save through the Qbix backend, provide platform pickers (Streams/userChooser, Streams/lookup, Users/web3/address), collaborate through Streams observation, and use `Q.Tool.mockup` mechanical renderers via `Q.Tool.DOMtoSVG`.
